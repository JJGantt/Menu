# Menu app (repo Menu)

iOS + watchOS reference app for one restaurant's menu, shown on devices as "Menu". xcodegen-generated
(`project.yml`). Team `XMH4AVFC78`. Bundle ids stay `com.jaredgantt.CapitalGrille` (+ `.watch`,
`.watch.widgets`): testers update in place, and the keychain service that holds each device's Anthropic
key is named after it.

**The code holds no restaurant data.** The menu, cocktails, dish photos, bottle catalog, every prompt
and the restaurant's name come from Supabase (below). Code says "the restaurant"; a prompt that names it
uses `{{restaurant}}`, filled from `app_config.restaurant_name`. Keep it that way: an example in a
prompt or tool description that names a dish, cocktail or bottle of ours belongs in the remote prompt
text, not in Swift.

## Getting a build onto Jared's devices: TestFlight, always
Every build reaches his iPhone and watch through TestFlight: `./scripts/release.sh` (see "TestFlight release" below, including which group he is in). Watch work in particular only ever goes this way. Do not build to a device id or `devicectl install` — that route needs his phone on the Mac's network and gets used by nobody.

To check that a change compiles first, build unsigned — `xcodegen generate` if `project.yml` changed, then `xcodebuild -project Menu.xcodeproj -scheme Menu -destination "generic/platform=iOS" CODE_SIGNING_ALLOWED=NO build`.

**Checking it in the simulator:** an unsigned build cannot use the keychain, so the assistant reports no API key. Sign it ad hoc instead (`CODE_SIGN_STYLE=Manual CODE_SIGN_IDENTITY=- DEVELOPMENT_TEAM=` against a simulator destination) and a Debug build seeds the key from `Secrets.swift`. Debug builds take launch arguments so nothing has to be typed or tapped: `-simSection cocktails` opens a tab, `-simSearch ribeye` searches, `-simAsk "<question>"` asks the assistant once the catalog is in (`xcrun simctl launch <sim> com.jaredgantt.CapitalGrille -simAsk "…"`, then `xcrun simctl io <sim> screenshot`). The answer also lands in `app_logs`.

## Watch install gotcha — "Could not install at this time"
Only bites a direct Mac→device install, which is not how builds ship (above).
Root cause: **Developer Mode on the watch is hidden until the system sees a dev-signed install attempt arrive via the direct Mac→Watch CoreDevice channel.** The iPhone→Watch app-relay path silently fails when Dev Mode is off, surfacing as an IDS socket timeout in `appconduitd` logs and a generic "Could not install at this time" dialog. App Store watch apps install fine because they don't need Dev Mode.

### Symptoms when Dev Mode is off on the watch
- Watch app install fails with "Could not install at this time"
- Console.app filtered on `appconduitd` shows: `IDSDeviceConnection has timed out waiting for a socket`, error `ACXErrorDomain Code=8 "Failed to create socket"`, underlying `com.apple.identityservices.error Code=20`
- Settings → Privacy & Security on the watch has no Developer Mode toggle (it's hidden)
- App Store watch apps install fine

### Fix
1. Verify Mac sees the watch in CoreDevice: `xcrun devicectl list devices`. If missing, kick remotepairingd:
   ```
   kill -9 $(launchctl list | awk '$3=="com.apple.CoreDevice.remotepairingd"{print $1}')
   ```
   Watch reappears within 15s as "connecting" → "connected (no DDI)".
2. Run a direct install to the watch UDID (will fail but triggers the dev path):
   ```
   xcrun devicectl device install app --device 15EAAA2F-0775-5655-839A-603F56EC9DE1 .../MenuWatch.app
   ```
   Fails with `Developer Mode is disabled` — but the toggle now appears on the watch.
3. On the watch: Settings → Privacy & Security → Developer Mode → ON. Watch restarts.
4. Re-run the install. Works going forward via either direct or iPhone-Watch app path.

## Architecture notes
- Shared chat engine at `MenuApp/ChatEngine.swift` — both iOS and watch use it
- **The watch keeps running wrist-down while it answers** (`MenuWatch/StayAwake.swift`): the
  watch target has `UIBackgroundModes: audio`, and while the chat is `thinking` (transcribing, then
  waiting on the model, or an order being taken) it holds the microphone and discards what it hears, so
  the answer lands and its tap comes with the wrist down instead of the app being suspended mid-request,
  for at most a minute per answer (his number; nothing restarts it until the chat stops thinking).
  Playing silence does not do this: a watch app that only plays is frozen when the wrist drops (an
  order's transcript was back from the hub in 1.6s and reached the watch 30s later). It does not speed
  up the dimmed screen's redraw.
- The phone pushes its Anthropic key to the watch over WatchConnectivity (`WatchKeySync` → `PhoneKeyReceiver`), so the watch never needs one typed in.
- **Watch voice input is recorded audio, not Apple dictation.** A press (double tap, or a tap on the screen) starts `VoiceCapture`/`Recorder` (ported from StatusHub's watch app) and the next press sends; nothing ends a recording on its own, and the x at the bottom throws away whatever is under way (the recording, or the question being transcribed and answered). While a question is worked on there is no spinner, status text or cancel screen — the edge is the indicator, as on StatusHub's watch. What the page does show, as on StatusHub's: the transcript the moment it is back (so a wrong one can be cancelled before it is answered), and under it each tool call as it is made, one small violet monospace line apiece; both give way to the answer when it lands. Each transcription try is capped at 15s plus half the clip's length (the upload grows with the clip: a 72s order is ~625 KB, about 14s on a good watch link), and a stuck one is retried, up to three tries, ending in the failure haptic if none lands. A clip that never became words is not deleted: the chat keeps it for "Tap to retry", the Orders page keeps it as an unsent row (below). The clip goes to the hub's `/api/cg/transcribe` (status-hub `server.js`), the same Groq Whisper as the hub's own voice input, authenticated by this device's Anthropic key as `X-Owner-Key` — so only the owner's device can transcribe; a tester's watch gets a 401. The edge of the glass shows the state as StatusHub's does (`VoiceBorder`: red while recording, white sweep while transcribing and answering). The hub's copy of the owner-key hash must change with `AppGate.ownerKeyHash`.
- **Getting to the watch app:** a Control Center button (`OpenControl`, watchOS 26) that opens it, and a blank complication (a clear view filling the slot — invisible on the face, still pressable) that opens it straight into a recording (`menuapp://record` → `VoiceCapture.requestRecording()`, started by the chat page once the app is active, so the haptic and chirp are the same as a tap; a request older than 20s lapses rather than firing on a later wrist raise). The complication exists twice, identical but for kind and name (`MenuComplication`, kind `CapitalGrilleComplication`, "Menu"; `BlankRecordComplication` "Menu Blank"), because a face can keep showing a cached old drawing of a kind; removing either drops it off any face holding it, so the kinds keep their old names. A third blank complication, `OrderComplication` "Menu Order", opens `menuapp://order`: straight to the Orders page, recording an order (owner only; on a tester's watch it just opens the app). `VoiceCapture.requestRecording(for:)` names which page a request is for, and only that page starts it. All are in `MenuWatchWidgets`. The button's `OpenAppIntent` is compiled into the watch app as well (`project.yml` lists it under the watch target's sources), because the system runs an `OpenIntent` in the app it opens. The app no longer runs a workout session, so it backgrounds like any other app and has no HealthKit entitlement.
- **Watch layout on the 46mm glass:** its corners are rounder than older watches', so nothing may sit in the ignored top safe area at the side edges. Pages either keep the safe area (Settings, the idle prompt) or start their first line 32pt down with 8pt side padding (the restock list, the chat history's inset) — the depth StatusHub's watch measured a full-width line clearing the corner. There are no page dots; the context is cleared from Settings, not from the chat page. The restock list is a plain stack, not a `List` (a watch List pads every row tall), with a two-press Clear all at the bottom.
- **Orders** (owner only — the watch page right of the chat, and the phone's Orders tab): a double tap on the watch's Orders page, or a tap anywhere on it that is not a row or Clear all, records a guest ordering, and the next press sends it. The clip goes to `/api/cg/transcribe` like a question, and is deleted once its orders are on the list: only text is kept. `OrderTaker` (`MenuApp/Orders.swift`, shared by both targets) works in TWO passes, one request each (`finishAfterTools`: the tool call is the answer, so no closing reply is asked for):
  1. **As heard** — the transcript and the open orders with their age, no menu; the model calls `add_orders` with each NEW item worded as said. The rows are on the list at once and the wrist is tapped. What counts as new is decided here, because it decides what is written: the read-back, a separately recorded confirmation and a guest's question about an item are not orders, and the prompt says so. That judgement is the model's — a matcher would get it wrong.
  2. **Standardized** — those rows (as JSON, each with its row id) and the whole menu with ids; the model calls `standardize` with a menu id for each row it can place. The stored name is the menu's own, looked up from the id; a row with no match, an unknown id, or one the model leaves out keeps its heard wording. Nothing is refused, and if this pass fails the heard rows are already listed. Each cocktail goes in with its ingredients, so a generic drink (an espresso martini) is matched to the one of ours it is (Kona Espresso). The id is read out of whatever the model returns for a row, because asked for the id it has returned the whole row line.
  **A bad connection loses nothing.** A recording that cannot be transcribed is kept on disk (`OrderOutbox`, Application Support, under its own interaction id) and shown at the top of the watch's list as an unsent row (a crossed-out cloud and its length; two taps throw it away). It goes again, oldest first, when the network comes back (`Connectivity`, an `NWPathMonitor` used only as a trigger), when the app comes to the front, and after any order lands — never on a timer — and stops at the first that still cannot go. If pass 1 fails after the transcript is back, the whole transcript goes on the list as one row (`orders_kept_as_heard` in `app_logs`); if even that write fails the clip is kept as unsent. A pass 2 failure (`orders_standardize_failed`) is not the order's: the rows are listed, so there is no failure buzz, and those same moments run the menu pass again over every row it never reached. the hub answers a second write under the same recording id with the rows already written, so neither that fallback nor a retry after a timeout lists an order twice. A row the second pass has not looked at yet (`standardized_at` null) is drawn dimmer on both surfaces. Which model runs each pass is a hub setting, `cg_orders_model_first` / `cg_orders_model_second` in `app_settings` (a model id), Sonnet when unset; the app reads it with the list, so switching needs no build. With pass 1's small prompt Sonnet answered as fast as Haiku (about 1.2s), and both handled every read-back and question case tried. The list is `cg_orders` (data-layer `00125`, `00126`), which has NO anon policy: it is reached only through the hub's owner-gated `/api/cg/orders` (GET; POST items as heard, answering with the saved rows; POST `/standardize`; POST `/done` with `{id}` or `{all: true}`), so testers neither see nor write it. Both double-tap bindings (chat and orders) check `onScreen`, set per page by `WatchContentView`, so only the page showing takes the gesture. `app_logs` has `orders_added` (output = how many), `orders_standardized`, `orders_standardize_failed`, `orders_done`, `orders_failed` (pass 1), `orders_kept_unsent`, `orders_unsent_discarded` and `orders_keep_failed` rows beside the usual `voice_*` ones; a resent recording's rows land under its original id.
- **Models and thinking** (`AIModel` in `ConfigModels.swift`): Haiku 4.5, Sonnet 5, Opus 5.5; the owner defaults to Sonnet. `thinkingParams` keeps answers fast: Sonnet runs with thinking disabled; Opus 5.5 rejects `disabled`, so it runs at `effort: low`.
- **Gating** (`AppGate`, `ConfigModels.swift`) limits which models a device may use: owner (the key whose hash matches `ownerKeyHash`) gets everything, anyone else Haiku, overridable per profile from the Supabase `app_config` table. `AIModel.current` quietly falls back to the default when the stored choice isn't allowed, so every app entry point must call `AppGate.apply()` at launch and again whenever the key changes — both targets do. Skip it and the device sits on the bundled restricted profile no matter what Settings shows.
- **`app_logs`** (every interaction, API request and tool call, written by `AppLogger`) is the record of what the assistant was asked and did. A watch voice question also writes `voice_*` rows (`VoiceLog`: recorded, transcribed, or where it failed) under the same `interaction_id`, so the whole path from press to answer is one query; the hub's side is a `voice_hub` row under the same id (when the clip arrived, upload and Groq times), since Fly keeps only minutes of its `[cg-transcribe]` stdout. `voice_phase` and `voice_stay_awake_expired` rows show the app going to the background mid-question and the awake minute running out. Writes are fire-and-forget. A batch that fails for the network is kept and sent with the next flush (up to 500 rows, in memory only, so a quit app loses them); one Supabase refuses is dropped silently — check Supabase's edge logs for `POST /rest/v1/app_logs` status codes when rows stop appearing.
- **The menu lives in Supabase**: `menu_groups` (each group's id, title, order and section order — lunch, dinner, …), `menu_dishes` rows (`menu` is a group id; `extra` keeps fields the app does not model), and the `app_content` `seasonal_programs` row. Dish photos are in the public storage bucket `dishes`, named by the file name in `menu_dishes.image` (`dishPhotoURL`). Adding a group or a section is a data change.
- **Weak signal and offline:** every read the app needs to work (`SupabaseClient.getCached`: menu, cocktails, prompt blocks, `app_config`, the bottle catalog and its reference tables) saves its last good answer in Application Support (`ResponseCache`) and falls back to it when the request fails; stores show that copy the moment they open, then refresh. A fresh install has no saved copy, so the build bundles one: `scripts/seed.sh` (run by `release.sh`) fetches the same reads with the same key into `Seed/<cache key>.json`, gitignored, and the fallback order is network → saved → seed. A new `getCached` read needs its line in `seed.sh`. Dish photos go through `RemoteImageCache` (URLCache on disk): every dish's photo is prefetched once the menu loads, and a failed revalidation falls back to the disk copy. A fresh install that has never been online shows no photos.
- **Seasonal programs** — the limited-time cards, any number at once, stored as ONE `app_content` row, key `seasonal_programs`, whose `data` is a JSON array in display order. Each program: `meta{title, dates_active, notes[]}`, `wines[]` (name/producer/region/varietal/description/tasting_notes/suggested_pairing/image_url), `sections[{title, paired_wines[], dishes[]}]`. Card titles, section headers, and the prompt summary all come from the data, so adding a card is a data change (append to the array), not a build. **A card is removed only when Jared says so** — a promotion's printed end date is not that. Section dishes are stubs; a stub whose `name` or `menu_name` normalizes to a regular-menu dish borrows that dish's qualitative recipe details in the detail view (never its portion, price, or calories). Chat reaches it through `get_seasonal_program`; the routing rule in the remote `base_rules` block uses `{{seasonal_tool}}` and `{{seasonal_skeleton}}` placeholders. The program's wines are deliberately NOT rows in `bottles` — that table is what the bar physically stocks.

## In-app AI assistant
`ChatEngine.swift` answers through the Anthropic API (`AnthropicClient.chatWithTools`), with its tools as the `AnthropicTool` handlers in the same file.

**Chat history carries each turn's tool calls** (`ChatTurn`/`ToolTrace` in `AnthropicClient.swift`), replayed to the model as real `tool_use`/`tool_result` blocks with long results cut. Sent as question/answer text alone, the model sees its own run of "Added X" answers with no tool behind them and starts claiming adds it never makes. `update_restock` takes each item as `add` (a change in count, which the handler applies to the list as freshly fetched, so the model never does arithmetic against its possibly stale copy) or `set` (an exact total; 0 removes) — an update with neither, such as the old `quantity` the model copies from earlier turns' tool calls in its history, rejects the whole call so the model resends it instead of the answer claiming an add that was dropped — answers with what each item went from and to and that the request is done, and takes a catalogued bottle's kind from the bottle's own row rather than the model. On the watch, the chat page and the restock page share one `BottleStore` and one `RestockStore` (owned by `WatchContentView`), so a voice add is already on the restock page and that page fetches only the list.

**Every write tool answers with the state as saved, read back after the write** — the restock item's new count, each bottle's locations, the area list, whether a delete or add matched a row — never an echo of what was requested, so the model reports what happened. That read-back is also the only refresh a write needs: bottle and area writes re-read just `bottles` + `bottle_areas` (`BottleStore.refreshBottles`, one round trip), and nothing is re-fetched after the answer, which is returned the moment the model finishes. The full `refreshFromSupabase` is seven round trips and about 220 KB, and stays on view load and pull-to-refresh only; run after every answer it held each watch answer about 3s. The restock list in the prompt is re-read at the start of every question (it is edited from other devices and cleared daily), and the prompt tells the model that counts from earlier in the conversation can be stale.

**The restock list empties at 6am Eastern every day** — a Supabase pg_cron job (`menu-restock-clear`, data-layer migrations `00121`, `00162`), not the app, so it happens with no device open. Not midnight, because a closing shift still uses the list after midnight.

**Cabinet restock** — the backup liquor cabinets' par sheets are the Supabase `cabinets` (`dark`, `light`; `note` is the sheet's own free-text line) and `cabinet_pars` tables (data-layer migration `00120`; `product_id` is a `bottles.id`, or a slug with kind `misc` for an uncatalogued item). Jared reads out what is in a cabinet and the model passes it, as catalog ids with counts, to `check_cabinet`, which does the comparison in code and returns the reply the model answers with: a "Missing" list and an "Over par" list, one bottle per line as "Name ×n". It writes to the restock list only when Jared asks (`add_to_restock`), raising each missing item to at least its shortfall (through the same path as `update_restock`, as `at_least`) — raised, never added to, so re-running a check never doubles the list, and "add those" after a check is the same call again with the flag set. The model only resolves names, by sound, to catalog ids (a bare brand is its plain bottle, a variant only when named); the tool refuses anything that is not a catalog id, so every par item must be a `bottles` row. Left to compare and format on its own it dropped par items he never read out and listed the shortfall instead of what was over par. Changing a par is a data edit, no build.

The **system prompt** is built in-app (`buildPromptAndTools`) from rule blocks that live **only in Supabase `app_content` (key=`system_prompt`, JSON `data`: restock/food_menu/base_rules/catalog_rules/cocktail_routing, plus orders_heard/orders_match for the two order passes)**; there is no in-code copy, and a missing block is simply left out. They use `{{tool}}`/`{{data}}` placeholders and `{{restaurant}}`, resolved at runtime (`ChatEngine.fill`). Update the remote block to change live behavior. `get_food_menu`'s section list and meal enum are built from `menu_groups`. The **catalog skeleton** injected into the cached prompt prefix is built dynamically from `bottleStore` — enrich it by editing `formatBottle`, no data migration. All app content (bottles, pairings, glossary, descriptions, views) is backend data: adding/editing content needs no rebuild; only a new grouping FIELD or new UI/tool needs a build.

## Bottle / wine / liquor data model
**Liquor and wine group differently** because their data has different shapes:
- **Wine** — two *orthogonal* view axes (separate toggles): "Type" (group_by `varietal`/`category`) and "Style" (group_by `pairing_style`). A style like "Structured Bold Red" crosses varietals, so style is NOT a subset of type — independent filters.
- **Liquor** — a single *nested* two-level tree in "Type" view: spirit **type → style (varietal) → bottle**. Style is a strict subset of type (every Bourbon is a Whiskey). The type→style mapping lives in the backend **`spirit_types`** table (varietal, type, type_order, style_order) — NOT hardcoded; a varietal with no row defaults to a type equal to itself (Vodka/Tequila render flat). Only **Whiskey** (~84 bottles) and **Brandy** (Cognac + Brandy) actually nest. Type-level umbrella descriptions are `group_descriptions` rows with `dimension='type'` (only "Whiskey" is custom); style-level reuses varietal blurbs. Code: `BottleStore.liquorTypeGroups()` → `[BottleTypeGroup]`; `LiquorListView` renders nested when `group_by == "varietal"`, flat otherwise.

Architecture preference: the **backend is the source of truth**; the app derives structure dynamically from relational data (e.g. a `section_views`/grouping table defines view modes). Do NOT stuff this config into an `app_content` JSON blob — use real relational tables.

## Working agreements (behavioral — these are firm)
- **Bottle catalog (`bottles` table):** NEVER add a bottle on my own initiative or from web research — the only valid reason a bottle exists is "we physically carry it," and only Jared knows that. Adding is allowed ONLY when he explicitly asks. **Editing/correcting and deleting ARE allowed without asking each time, once I've confirmed the facts via sources** (e.g. delete a phantom row, enrich a tasting note).
